# 天凤牌谱分析 v1.3.0

> **这是开发过程记录（旧版 README，随每次改动持续更新）**：包含需求来源（用户 mXXXXX）、实现方法、测试、踩坑与版本历史，面向开发者查询；面向使用者的发布说明见仓库根目录的 `readme.md`。

把天凤（tenhou.net）的 `.tenhou` 牌谱（旧 `.xml` 仍认）、NAGA（naga.dmv.nico）的报告（`.naga`，旧 `.json.gz` 仍认）与 Mortal（mjai.ekyu.moe）的复盘报告（`.mortal-a` / `.mortal-b` / `.mortal-c`）在本地解析成「逐帧状态」，
打点出 **40 个牌谱特征**（5 个第零类 + 17 个第一类 + 17 个第二类 + 1 个第三类）存进 SQLite 数据库（三类牌谱可以混编进同一个库），
再用网页回放牌局、按特征检索局面、把当前帧的全部特征值并排显示。全部在本机运行（只有「牌谱下载」会联网）。

- 前端：`web/index.html` + `web/js/`（原生 JS，无框架、无构建步骤）
- 后端：`mjscore/`（Python 标准库）+ 可选的 Node.js 打点
- 数据库：SQLite，默认放在 `data/db/`

## 1. 功能

| 页签 | 能做什么 |
| --- | --- |
| **首页 / 播放** | 选择本地牌谱或载入示例 → 牌桌、牌河、副露、和了信息、事件列表（点击跳帧）。键盘：`←/→` 上一帧 / 下一帧，`↑/↓` 上一事件 / 下一事件，`Home/End` 首帧 / 末帧，`PgUp/PgDn` 上一局 / 下一局。可以隐藏他家手牌、复制当前帧的特征串 |

界面右上角显示版本号（`v1.3.0`），数据库里也记录生成它的软件版本（见第 5 节）。

### 1.1 检索条件的写法

- 互斥取值的特征（局况、是否南三局及以后、自家、自家立直状态、自家副露状态、亲家（他家）立直状态、亲家（他家）副露状态）用**下拉框**选择。
- 第零类特征（NAGA-平衡 分析 / NAGA-超副露 分析 / Mortal-4.1-避四 分析 / Mortal-4.1-平衡 分析 / Mortal-4.1-争一 分析）**不出现在这个下拉里** —— 它们改用 4.3 的四种互斥检索方案（用户 m04556 ③）。
- 整数 / 实数特征用文本框，支持四种写法：

| 写法 | 含义 |
| --- | --- |
| `3` | 等于 3 |
| `1-30` | 区间（含两端） |
| `1,2,3` | 列表（任意一个即可） |
| `>=3` | 比较（`>` `>=` `<` `<=` 都行，实数如 `>=0.5` 也可以） |

多个条件之间是 **AND**：每个条件都要同时满足，所以条件越多结果越少。先用「全部浏览」确认库里有数据，再逐步加条件。

三种**向听数**特征比较特殊：内部取值是整数 `-1 / 0 / 1 / 2 / 3`（`3` 表示「>=3 向听」），
界面与本文档把它**显示**成 `>=3`，但**检索时仍按内部整数匹配** —— 填 `3`、`3-5`、`>=3`
都会命中内部值为 3 的帧（`>=3` 只是展示口径，不改变匹配逻辑）。

## 2. 40 个特征

### 2.1 第零类特征（5 个，**按帧判定**：这一帧有没有该模型的决策数据）

逐个打点帧判定「这一帧能不能用上某款 AI 模型的决策数据」：取值「是」当且仅当**这一帧做决策的那名玩家带该模型的决策概率表**（`dahai_pred` / `reach` / `kan` 属于这一帧的 actor，`huro` 只看这名玩家那一格；用户 m06323 ①，口径按用户 m06560 更正 —— 第 60 轮首版还要求「这一帧由牌谱初始的主视角决策」，该条件已删除；此前的口径是整份牌谱一个值）。牌谱里含哪些模型由 NAGA 报告的 `naga_types` / Mortal 报告的 `review.model_tag` 判定（天凤牌谱五项都是「否」）；（附带说明）**牌谱初始的主视角**（`meta.viewer_seat`）只用来决定播放时把谁放到主视角 —— NAGA 报告取官方 viewer 的默认视角（`tw=0`，即报告 0 号座位），Mortal 报告取 `review.player_id`（报告只复盘这一家）；它与第零类判定无关。顺序固定为：

| 特征名 | 取值 |
| --- | --- |
| NAGA-平衡 分析 | 是 / 否（原第一类特征「NAGA决策」，用户 m04556 ② 改名并移入第零类） |
| NAGA-超副露 分析 | 是 / 否 |
| Mortal-4.1-避四 分析 | 是 / 否（Mortal 报告的 `model_tag = 4.1a`，用户 m05937 ②） |
| Mortal-4.1-平衡 分析 | 是 / 否（`4.1b`；报告里没给 `model_tag` 时按平衡处理） |
| Mortal-4.1-争一 分析 | 是 / 否（`4.1c`） |

模型名按用户 m04556 ③ 的命名规则「`<系列名称>-<版本号>-<风格>`」或「`<系列名称>-<风格>`」规范化（系列 = 第一个短横线之前的字符串，如 `NAGA` / `Mortal`）：报告里的原始名 `ニシキ` → `NAGA-平衡`、`カガシ` → `NAGA-超副露`、`4.1a` → `Mortal-4.1-避四`、`4.1b` → `Mortal-4.1-平衡`、`4.1c` → `Mortal-4.1-争一`（其它 `ヒバカリ` / `オメガ` / `ガンマ` / `ニュー` / `シグマ` → `NAGA-<原名>`，裸版本号如 `4.0` → `Mortal-4.0-平衡`；官网与官方 viewer 的 JS 里查不到「超副露 / バランス」字样，这两个别名是按用户给的标签写的）。

**第零类特征不参与「添加特征词条再填取值」的检索方式**，改用 4.3 里的四种互斥方案；因为它是按帧判定的，检索命中的就是「这些帧自己满足方案」的帧（同一份牌谱里有的帧命中、有的不命中，用户 m06323 ①）。

### 2.3 第二类特征（17 个，需要算法）

**三种向听数**（国士無双 / 七対子 / 面子手）：`-1` = 已和牌，`0` = 未和牌但听牌，`1` / `2` / `>=3`。
内部取值为整数 `-1 / 0 / 1 / 2 / 3`（`3` = 「还差 3 次以上」），界面与文档统一显示成 `>=3`；
检索条件仍按内部整数匹配（见 1.1）。
定义：为达到听牌状态，最少还要摸进或副露的牌张数。计算时会扣掉「场上已经看得见的牌」，所以不会出现期待第 5 张的胡想。

**六个期望听牌枚数**（副露自摸 / 副露荣和 / 立直·默听，各分「期望枚数」与「绝对枚数」）：非负实数，已和牌的帧记 0。
「期望枚数」= 在「达到听牌」的前提下，能达成满足起和役的和牌的牌张数的期望；「绝对枚数」不看场上可见牌，只数自身手牌能和的张数。
「立直·默听」两项对门清帧计算，副露帧为 0；带「副露」字样的四项即使当前是门清手牌也按副露状态（起和役与番数）计算。

**六个期望打点**（副露荣和 / 副露自摸 / 立直荣和 / 立直自摸 / 默听荣和 / 默听自摸）：正实数，已和牌的帧记该手牌的实际和牌得点。
「立直」= 假想保持门清直到听牌并在听牌时宣布立直（已经宣布立直时用实际的番数）；「默听」= 假想不宣布立直。副露帧的立直项为 0。
计算按天凤段位战规则（含本场 / 供托 / 宝牌，不含一发、里宝、槍槓、嶺上、海底、河底等偶发与特殊役）。

**两个危险特征**（以当前摸牌者为主视角）：其他家无人立直时为 `-1`。
- 立直家（他家）危险筋组数量：0 ~ 18
- 立直家（他家）危险两面组数：0 ~ 288

（每个特征的精确定义、口径与验证过程都写在 `log.md` 的第 11 / 13 / 14 节。）

### 2.4 第三类特征（1 个，用户 m07289）
第一类里的「等待鸣牌」在第 63 轮按用户 m07289 改成**第三类特征**：它**不参与**「添加特征词条 → 填取值」的检索流程，也**不列进**播放界面右侧的「当前帧特征」面板（那一列改由面板底部的**大号文字**「出牌局面 / 鸣牌响应局面」体现）。检索侧改为在第零类框**右端**的一个**必选单选**里选「出牌」（= 这一帧不是鸣牌响应帧）或「鸣牌响应」（= 这一帧是鸣牌响应帧），服务端按列 `f_meld_wait` 过滤，与其它条件 **AND**（默认「出牌」；只放上下两行选项，不写标题与说明文字）。
| 特征 | 取值 | 说明 |
| --- | --- | --- |
| 等待鸣牌 | 是 / 否 | 「是」= 这一帧是**鸣牌响应帧** —— 有玩家打出一张牌、而这张牌**可能被他家鸣牌**（判据见下），此时**可能鸣牌的那一家各占 1 行**（用户 m07289 ①）；其余帧（非自摸的摸牌帧、吃 / 碰 后等待出牌的帧）都是「否」 |
判据（用户 m07289 ① 的严格定义 = **看是否可能被他家鸣牌，而不是牌谱里实际有没有出现鸣牌**）：
- **碰 / 大明杠**：另外三家里有**未立直**的一家手里有同种 ≥ 2 张；
- **吃**：只有出牌者的**下家**能吃（吃只能吃上家），且牌是数牌、下家手里有成顺的两张，**并且吃完之后至少还有一张能打的牌**（吃牌后打出的牌不能与被吃的两张牌组成顺子 = 禁止食替；下家手牌一旦鸣牌就因食替无牌可打时视为**不能吃**）；
- 已经立直的家不能鸣牌，因此不计；
- **仅可能被荣和**（没人可能鸣牌）的出牌帧**不算**（用户 m07289 ③：他家能与杠牌交互的唯一场景是枪杠和牌，遵循 NAGA「能和就和」的原则，构不成决策点）；
- **立直宣言 / 杠宣言都视为出牌动作**（立直 / 暗杠 / 加杠是出牌阶段的可选策略）：立直宣言牌按普通出牌进入上面的判据，**暗杠 / 加杠 / 大明杠的展示帧一律忽略**，**自摸帧一律忽略**。

## 3. 安装（Windows 10 / 11，从零开始）

### 3.1 需要什么

| 需要 | 说明 |
| --- | --- |
| **Python 3.8+**（推荐 3.10 及以上） | 必需。**不需要任何第三方包**，只用 Python 标准库 |
| **Node.js 18+**（可选） | 装了打点更快（`node` 跑前端同一份 JS 解析器）；不装也行，全部特征由 python 打点 |
| 浏览器 | Edge / Chrome 等现代浏览器 |
| 硬盘 | 数据库会占空间：勾选「写入原始数据」时约为每个打点帧 200~400 字节（33k 帧的库约 35 MB～） |

### 3.2 安装 Python

1. 打开 <https://www.python.org/downloads/windows/>，下载 64-bit 安装包。
2. 运行安装包，**务必勾选「Add python.exe to PATH」**，再点 *Install Now*。
3. 验证：按 `Win+R` → 输入 `cmd` 回车 → 输入

   ```
   python --version
   ```

   能打印 `Python 3.x.y` 即可（如果提示「不是内部或外部命令」，重装并确认勾选了 PATH；用 Anaconda 的话请改用 *Anaconda Prompt*）。

### 3.3 安装 Node.js（可跳过）

1. 打开 <https://nodejs.org/>，下载 LTS 版，一路「下一步」（同样保持 PATH 勾选）。
2. 验证：`node -v`。
3. 装在非默认位置时，程序会按这个顺序找 node：环境变量 `MJSCORE_NODE` → `C:\Program Files\nodejs\node.exe` → `D:\Program Files\nodejs\node.exe` → `D:\Program Files (x86)\nodejs\node.exe` → `PATH`。
   例如：`set MJSCORE_NODE=D:\tools\nodejs\node.exe`

### 3.4 准备项目

把整个项目文件夹放到任意目录（尽量别用中文路径和空格），例如：

```
D:\tools\tenhou-paipu-analysis
```

### 3.5 启动

在项目根目录打开 PowerShell（文件资源管理器地址栏输入 `powershell` 回车），然后：

```powershell
cd D:\tools\tenhou-paipu-analysis
python server.py
```

看到 `http://127.0.0.1:8770/` 后，用浏览器打开它。

> **不要直接双击 `web/index.html`**：`file://` 下浏览器不允许访问本地接口，「牌谱分析」「牌谱检索」都用不了。
>
> 端口被占用时：`python server.py --port 9000`，然后打开 `http://127.0.0.1:9000/`。
>
> 关闭服务：在 PowerShell 窗口按 `Ctrl+C`。

## 4. 使用流程

### 4.1 准备牌谱（`data/paipu/…`）

两种来源，效果一样，下载/保存到哪都行，分析时填那个目录即可。

**a) 网页「牌谱下载」**

1. 打开「牌谱下载」页签，选择输入方式：单个 url，或一个「每行一个 url」的文本文件（`#` 开头的行会被忽略）。
2. 指定本地存储地址：默认 `data/paipu/<时间戳>`（如 `data/paipu/20261007-165558`）；`data/paipu` 是固定的根目录，只有最后一段子目录名可以自定义。
3. 点「下载」，界面会显示待下载数量与成功 / 失败数量。同名文件的取舍按牌谱类型与 NAGA 来源区分：天凤牌谱发现本地已有同名 `<特征码>.tenhou` 就**跳过、不重复下载**（不再覆盖，也不发请求）；下面说 NAGA 报告：NAGA 报告里官方 `naga.dmv.nico` 来源发现本地已有同名报告就**跳过、不会重复下载**，`ricochet` 来源则**重新下载并覆盖同名文件**（ricochet 带 `mtd`，会多出 NAGA-超副露 / Mortal 系模型；用不同来源的链接重新下载同一张牌谱就能把它换成模型更多的版本）；Mortal 报告（`https://mjai.ekyu.moe/report/<id>.json`）本地已有同名报告（`.mortal-a` / `.mortal-b` / `.mortal-c` 都算）就跳过，落盘后缀由报告里的 `review.model_tag` 决定（`4.1a` → `.mortal-a` 避四、`4.1b` → `.mortal-b` 平衡、`4.1c` → `.mortal-c` 争一；认不出的版本落 `.mortal`）。同一次下载里同一个来源的重复 url 仍算重复；`--no-overwrite`（命令行）时两种来源都跳过；对天凤牌谱而言这个参数与默认行为一致（都是同名跳过）。

**b) 命令行**


### 4.2 分析入库

1. 打开「牌谱分析」，在「**牌谱目录**」下拉里选一个目录（只列 `data/paipu` 下的子目录，例如 `data/paipu/20261007-165558`），点「扫描」递归列出它里面的牌谱；也可以直接在「**牌谱文件**」下拉里选单个牌谱（此时只分析这一个文件）。
2. 在列表里勾选要分析的牌谱（可「全选 / 全不选」）。
3. 选数据库：
   - **新建数据库**：填数据库名（默认 `paipu`）→ 生成 `data\db\<名字>.sqlite`（已存在则覆盖该库自己的记录，不删其它库）。
   - **扩充现有数据库**：从下拉框选一个已有库（显示 `名字（N 行 · v1.3.0）`）。本次分析结果会**追加**进这个库；**特征码相同的牌谱自动跳过**，不会重复写。数据库里记录着生成它的软件版本，**版本不一致的库在下拉框里标「⚠ 版本过低」且不可选**（提示写明只需删除后重新分析）。
   - 两个入口互斥：选「扩充」时数据库名输入框会被禁用。
4. 需要的话勾选「**同时写入原始数据（--full）**」（见 5.3）。
5. 点「分析」，进度条会显示已完成 / 总数、当前正在分析的牌谱特征码、局进度与耗时；完成后提示「完成：N 个牌谱 / M 局 / 打点 K 行（库内共 …）」以及扩充时跳过几个牌谱。

分析速度参考（本机开发沙箱实测，2026/10）：每个「打点帧」约 **115～132 ms**，与牌谱来源基本无关 —— 天凤 `.tenhou` 115.4 ms/帧、
NAGA `.naga` 131.5 ms/帧（转换成内部结构只花 0.05～0.08 秒/份，naga 仅多约 14%）。cProfile 显示约 **98% 的时间花在第二类特征
「期望枚数」的向听搜索**（`shanten.take` 上千万次调用），第一类特征合计不到 0.1%；写库本身只占 0.0x 秒。
所以觉得「NAGA 比天凤慢很多倍」的主要原因是**帧总量差异**：NAGA 一份报告 12～16 局 ≈ 600 个打点帧 ≈ 每份约 80 秒（41 份报告约 55 分钟），
而天凤目录往往文件少、局数少。旧参考值（更慢的机器）：5 个牌谱（2786 个打点帧）全新分析约 11 分钟；71 个牌谱（37254 个打点帧）量级为数小时。
想更快可以：`--tool node` 提升有限（瓶颈在第二类特征，两条路径都用 python 算），或分批 + 「扩充现有数据库」逐步累积。
**建议分批分析并用「扩充现有数据库」逐步累积**，每个批次随时可用。

### 4.3 检索与浏览

1. 打开「牌谱检索」，在「本地数据库文件」下拉里选库（下拉会显示行数与版本），或直接填路径。
2. （可选）在「牌谱特征」框**上方**的**第零类特征**框（标题已按用户 m07289 改成「**是否具有AI决策**」）里选一个互斥方案：「任意AI决策」= 报告含任意一种 AI 模型的分析结果；「NAGA决策」= 含任意一种 NAGA 系列；「Mortal决策」= 含任意一种 Mortal 系列；「同时具有」= 下方出现 5 个**方形多选框**（可多选），要求**被勾选的全部为「是」**。第零类方案与下面的第一、二类条件是 **AND** 关系。**不做选择 = 不筛选**（与旧版的检索行为一致）。同一个框的**右端**是第 63 轮（用户 m07289）新增的**必选单选**「**出牌 / 鸣牌响应**」（默认「出牌」，只放两行选项、不写标题与说明文字）：「出牌」= 只检索 `kind != 'wait'` 的出牌帧，「鸣牌响应」= 只检索 `kind == 'wait'` 的鸣牌响应帧（判据见 2.4）；它同样与全部条件 **AND**（服务端按列 `f_meld_wait` 过滤）。
3. 从「牌谱特征」下拉里挑一个特征 →「添加」→ 填 / 选条件（写法见 1.1）。不想要的行点「删除」，「清空」清掉全部条件。
4. 「检索」：返回所有满足全部条件的打点帧（列表顶部显示总条数）。「全部浏览」：按顺序翻阅整库。
5. 点任意条目 → 跳到该帧；右侧「当前帧」面板列出 **34 个特征名 = 取值**（40 个里的第零类 5 项不在这里列出 —— 决策表那一列已经蕴含了该信息，用户 m05937 ②；第三类「等待鸣牌」也不在面板里，改由面板底部的**大号文字**「出牌局面 / 鸣牌响应局面」体现，用户 m07289），其中当前检索用到的条目会高亮；顶部显示「当前帧的特征串」（牌谱特征码 + 局况 + 本场 + 巡目 + 风位，点一下可复制）。
6. 条目模式（静态帧播放）下，牌桌下方的**播放控制面板整块禁用**（灰掉、点了不响应）—— 只能通过右上角的「上一条目 / 下一条目」在检索结果之间切换；同时固定显示他家手牌（见 4.4）。

> 只有「非自摸的摸牌帧」、「吃 / 碰 后等待出牌的帧」与「鸣牌响应帧」（打出这张牌后、可能鸣牌的那一家各一行）才有特征值；其它帧（摸牌后马上自摸、以及杠后的岭上帧等）面板里会说明没有对应的打点行。
> 检索范围（静态帧集合）只由牌局决定：四家的决策帧都会被检索到，**与这一帧有没有 AI 决策概率向量无关**（用户 m06670）——Mortal 报告只复盘一家，别家的决策帧照样进检索结果，只是那些帧没有 AI 专属数据（概率条 / 决策表留空）。

### 4.4 回放

首页进入「牌谱播放」后，用「浏览选择…」打开本地牌谱，或切到「按特征码搜索」在已下载的牌谱里按特征码搜索，也可以把牌谱文件直接拖到牌桌区域；也可以用「牌谱分析 / 检索」跳到某个帧。播放视图支持：
- 播放视图的入口（页签「牌谱播放」与首页的「牌谱播放」卡片）统一走同一条状态机：**「牌谱检索 / 全部浏览」的静态帧不算「牌谱播放」状态** —— 在静态帧下点入口会先把牌谱卸载、回到「等待选择」的播放界面（入口栏 + 拖放提示、牌桌清空、NAGA 决策与当前帧特征面板留空），不会出现入口栏叠在旧牌桌上面的混乱画面；正常播放一个已载入的牌谱时点入口只是切回播放视图（牌谱不卸载）。手动「浏览选择…」或拖入新牌谱会退出静态帧条目模式（检索结果的条目表保留，回「牌谱检索」点一行仍能重新载入并回到条目模式）。

- 牌桌：手牌、副露、牌河、宝牌指示牌、供托、各家分数 / 风位、和了信息（役种 / 符 / 番 / 得点）。副露只用牌型表示（被鸣的那张横放），不在侧边写「吃 / 碰 / 杠」文字（用户 m04160 ②）；副露种类仍保留在 DOM 的 class 与事件列表里。**桌面上所有牌一律同尺寸**（第 66 轮起主视角的手牌 / 摸牌槽位不再放大 1.15 倍，用户 m08319 ③）；**加杠的第 4 张牌与原来那张横牌同列、正上方错开一整张牌宽**（官方 viewer 的 `kanPai` 画法，用户 m08319 ④）；**牌河每排 6 张、最多 3 排** —— 前 2 排各 6 张，**第 13 张起全部在第 3 排向右延伸**（第 66 轮起不再放入第 4 排，用户 m08576；CSS 仍按 4 排预留高度，所以牌河变长时手牌位置不跳）。**杠的名称一律用规范术语**（用户 m08623）：**暗杠** = 四张在手里、**加杠** = 三张已在副露区碰出 + 第四张在手里、**大明杠** = 三张在手里 + 第四张由他家打出。
- 牌河里的牌会按状态描边（用户 m07820 ⑤⑥）：**被鸣走的牌**用红框（`#e0503a`）、**被荣和的铳牌**用绿框（主题色）、**牌谱检索静态帧的「鸣牌响应局面」里被响应者等待鸣牌的那张打出牌**用黄框（`#ffd54a`，尺寸与红 / 绿框一致）。三种框都抬到**最上层**（`z-index: 1`，画在同一家面板里其它牌之上），但**同一家的不同牌张之间仍按打出的先后**（后打出的牌在上）；框比第一版**缩小一圈**（外扩 0.14 张牌宽、内描边 0.08 张牌宽，原来 0.17 / 0.11 —— 不缩太细）。黄框只在 `App.itemIndex >= 0`（检索 / 全部浏览的静态帧）且这一帧是鸣牌响应帧时画，正常播放不画。
- **细红框**（用户 m08125 ② / m08178）：当前帧是「出牌局面」时，把**这一帧的决策者**接下来**要打出的那张牌**在他自己的手牌（含刚摸到的牌）里用细红框标出来 —— **不限定主视角**（用户 m08319 ①：谁在这一帧做决策就把框画在谁手里；静态帧的主视角本来就会被调成决策者，所以静态帧看起来依旧是「框主视角」） —— 框比牌河的鸣牌红框更细（`inset 0 0 0 0.06 张牌宽` 的 `#e0503a`），同种牌取**最靠左的那一张**（5m / 5p / 5s 与概率条同一套规则：优先普通 5、避开赤 5）；**立直宣言**视为打出宣言牌（框跟着那张宣言牌）。实际动作为**暗杠 / 加杠**时，把**准备杠的 4 张牌全部**框出（暗杠 = 手里的 4 张；加杠 = 手里 1 张 + 副露区那 3 张，用状态里的准确牌 ID，所以副露区也会被框到）。细红框的图层与牌河红框一致（`z-index: 1`，同一家面板里画在其它牌之上、靠后打出的在上）。决策者本帧没有「下一步打牌 / 杠」的帧都不画（鸣牌响应局面要决定的是吃 / 碰 / 杠 / 过，不画）。
- 牌谱文件名右边有「复制url」按钮：点一下就把这条牌谱的**原始 URL** 复制到剪贴板（天凤 = `http://tenhou.net/0/?log=<log_id>&tw=0`，NAGA = `https://naga.dmv.nico/htmls/report_viewer.html?report_id=<report_id>&tw=0`，Mortal = `https://mjai.ekyu.moe/report/<report_id>.json`，**不会还原成 ricochet 的地址**），复制成功后按钮短暂显示「已复制」；正常播放与「牌谱检索」的静态帧播放都用得到（同一个工具栏）。特征码来自文件名（天凤 `<log_id>.tenhou`、NAGA `<report_id>.naga`，旧后缀仍认），「牌谱分析 / 检索」跳过来的静态帧也一样。
- 事件列表：**常态显示**（右上角已没有开关），点击任意一行跳到那一帧。
- 键盘：`←/→` 帧、`↑/↓` 决策帧（同「上一决策 / 下一决策」）、`Home/End` 首末帧、`PgUp/PgDn` 换局。
- 「上一决策 / 下一决策」只在**有待玩家做决策的帧**之间跳：摸牌后 / 吃碰杠后（等待出牌、立直、杠、自摸）与有人打出牌后**可能被他家鸣牌**的帧（「鸣牌响应」，可能鸣牌的那一家各停一次，判据见 2.4）。按用户 m07289 ①②③：立直宣言 / 杠宣言都视为**出牌动作**（跟着出牌帧一起判「能不能被他家鸣牌」），**立直宣言帧本身不再单独停留**；暗杠 / 加杠的展示帧与自摸帧一律忽略（他家只能枪杠和牌、能和就和，构不成决策点）。没人可能鸣牌的出牌帧不算决策帧（即便这张牌可能被荣和）（所以「下一决策」会直接跳到下一次摸牌，不再停在刚打完某张牌的画面上），新宝牌 / 和了 / 流局同样只是执行或展示帧。**判据只看牌局本身，与「这一帧有没有 AI 决策概率向量」无关**（用户 m06670）：「决策帧」= 需要某位玩家做出选择的帧，「有决策概率向量的帧」= 有某个 AI 模型给出分析结果的帧 —— NAGA 报告覆盖四家时两者恰好等价，Mortal 报告只复盘一家（概率向量只出现在被复盘那一家决策的帧上），这时若拿「有概率向量」当判据，「上一 / 下一决策」就会退化成「上一 / 下一自家决策」（第 61 轮修正）。有人打出牌之后、**可能鸣牌**的那几家各有一个「鸣牌响应」（吃 / 碰 / 杠 / 过）的决策帧；第 62 轮起这类帧会进数据库、可被检索，第 63 轮起判据改为「可能被他家鸣牌」且**只给可能鸣牌的那一家各打 1 行**（用户 m07289 ①），「上一 / 下一自家决策」只在主视角本人就是那位决策者时才停在这类帧上（用户 m07289 ⑤）。实测用户截图那份 9 局报告的第 0 局：132 帧里 64 帧是关键帧。本局内已经没有符合要求的帧时，「下一决策 / 下一自家决策」不会变灰，而是跳到本局结算帧；已经在本局结算帧时再点就跳到下一局开局（用户 m05277 ③）。反过来，「上一决策 / 上一自家决策」在本局里找不到目标帧时也不变灰 —— 退回本局开局，已经在本局开局时再点就退回上一局结算（用户 m05350）。

- 控制面板是**两行七列**（整块仍是 50px 高，牌桌尺寸与位置不变，用户 m05131 ④）：上排 = 上一局 / 下一局 / 上一决策 / 下一决策 / 上一步 / 下一步 / 切换主视角；下排 = 开局 / 完场 / 本局开始 / 本局结算 / 上一自家决策 / 下一自家决策 / 隐藏他家手牌。其中「上一决策 / 下一决策」就是原来的「上一关键 / 下一关键」，「本局开始 / 本局结算」就是原来的「开局 / 本局结束」；「开局」跳整个牌谱的第 0 局第 0 帧，「完场」跳最后一局的最终帧并直接跳出完场结算框，「上一 / 下一自家决策」只在**等待主视角做决策**的关键帧之间跳（决策者按被扫描的那一帧判断）。带竖线的按钮统一用整字宽的 `|`（本局开始 / 本局结算）与 `‖`（整个牌谱的开局 / 完场，U+2016），不再用积分延长符 `⎮` —— 它的字形偏高，看起来像竖线向上错位（用户 m05131 ③）。原先的「自动播放」按钮与功能、以及控制面板下方那条当前事件信息都已删除。「下一步 / 下一决策 / 下一自家决策」在本局里找不到目标帧时都不会变灰 —— 点一下跳到本局结算帧，在结算帧再点就进下一局开局（最后一局的结算帧则等同于「完场」，即跳出完场结算框）；「完场」按钮只在**已经弹出结算框**的时候才灰（用户 m05277 ②③）。反过来「上一步 / 上一决策 / 上一自家决策」在本局里找不到目标帧时也不会变灰 —— 点一下退回本局开局，在本局开局再点就退回上一局结算；第 0 局开局无处可退，停在原地（用户 m05350）。
- **完场结算框**（用户 m05131 ②）：在每个牌谱的**最终帧之后再点一次「下一步」**才跳出 —— 黑底（`rgba(0, 0, 0, .78)`）半透明、白字大字号、居中盖在牌桌上，每行一个排名、按最终得点从高到低（例如 `1位   玩家ID   35200`），支持中 / 日文字符。它和日语大字一样是**浮层**：不改变帧号、不算一步、也不进「牌谱检索」的结果（静态帧条目模式下不画）。离开最终帧（上一步 / 换局 / 点其他跳转）立即收起；「完场」按钮则可以直接跳到最终帧并让它跳出来，而且**无论当前在哪一帧都可以点**（只有已经弹出结算框时才灰）。结算框宽度至少 15 张牌宽、三列间距更大，够放较长的玩家 ID（再长就在框内用省略号收尾），文字上下的留白与行间距也比第一版更宽（用户 m05277 ①）。

## 5. 数据库

### 5.1 位置与结构

- 默认路径：`data\db\<数据库名>.sqlite`（数据库名默认 `paipu`）。
- 表：
  - `meta`：库级信息（`schema_version` 结构版本、`app_version` 生成它的软件版本、行数 / 牌谱数 / 局数、创建与更新时间、是否写入原始数据等）
  - `feature_def`：40 个特征的定义（名字 / 类型 / 取值域）
  - `source`：已入库牌谱（**按特征码 log_id 唯一**）→ 扩充时的判重依据
  - `round` / `frame`：逐局、逐打点帧的定位信息与 40 个特征值（外加第零类辅助列 `ai_models` / `ai_series`，检索时按系列聚合用）
  - `frame_full`：勾选「写入原始数据」时才有内容（逐帧的手牌 / 副露 / 宝牌 / 分数）

### 5.2 版本匹配规则

| 情况 | 结果 |
| --- | --- |
| 结构版本（`schema_version`）与当前软件不同 | 拒绝加载 / 扩充，提示「**数据库版本过低**……请删除后重新分析」 |
| `app_version` 与当前软件不同 | 拒绝加载 / 扩充（数据库格式可能已变），提示「**数据库版本不匹配**……请删除后重新分析」，或改用建库时的软件版本 |
| 没有 `app_version` 记录（第 22 轮之前建的库） | 按兼容处理，可以加载 / 扩充 |

删除一个库：`python tools/analyze.py --delete-db <数据库名>`。

### 5.3 「同时写入原始数据（--full）」勾选与不勾选

- **勾选**：除 40 个特征值外，还把该帧的原始数据（手牌 / 副露 / 宝牌指示牌 / 分数 / 牌谱路径）写进 `frame_full` 表。以后新增特征时，可以只按这些原始数据重算，**不必重新解析 XML**；代价是数据库约大一倍、写库略慢。
- **不勾选**：只写 40 个特征值与定位信息，库更小、写库更快；但**以后新增特征只能重新分析全部牌谱**。

### 5.4 为什么「扩充」会跳过牌谱

`source` 表以**牌谱特征码（log_id）**为主键记录已经入库的牌谱，扩充时按它判重：已经有的直接跳过，不会重复写入。
所以即使不先自己判重，也可以放心地重复把同一个目录拿去「扩充」。整批都是旧牌谱时会直接提示「这 N 个牌谱都已经在数据库里了」。

### 5.5 移动牌谱文件

移动 / 重命名 `data/paipu/...` 下的牌谱**不影响已有数据库**：检索、回放、特征面板都只读数据库。

## 7. 常见问题

| 现象 | 处理 |
| --- | --- |
| 页面提示「连不上本地服务」 | 先在项目根目录运行 `python server.py`，再用它打印的 `http://127.0.0.1:8770/` 打开（不要用 `file://`） |
| 分析很慢 | 打点本身比较重（尤其第二类特征）。可以先只分析一小批，用「扩充现有数据库」慢慢累积；机器上装了 node 会自动用 node 打第一类特征 |
| 提示找不到 node | 只影响速度，程序会自动全部改用 python。想用 node 就安装 Node.js，或 `set MJSCORE_NODE=...\node.exe` |
| 提示「数据库版本过低 / 版本不匹配」 | 该库是旧版本软件建的（schema ≤ 9，即 v1.3.0 以前的库不再支持）：用建库时的软件版本打开，或 `python tools/analyze.py --delete-db <库名>` 后重新分析 |
| 检索结果很少 / 没有 | 条件之间是 AND，越多越少；先「全部浏览」确认库里有数据，再逐个加条件 |
| 端口 8770 被占用 | `python server.py --port 9000` |
| 忘记库名 / 有哪些库 | `python tools/analyze.py --list-dbs`，或看 `data\db\` 目录 |
| 想换打点工具 | 不用换：默认自动（第一类走 node、第二类由 python 补齐），两种结果逐字段一致 |

## 9. 打包发布（Windows，可选）

普通用户不需要这一节；只有要把项目打成安装包（分发用）时才用到。

**准备**：`D:\coding\anaconda3\envs\py314_null` 里装好 PyInstaller（`python -m pip install pyinstaller`，要 >= 6.19 才支持 Python 3.14）；在项目根执行一次 `npm install`（Electron + electron-builder，首次会下载约 100 MB）。

**一键打包**（在项目根、用普通（非受限）终端）：

    powershell -ExecutionPolicy Bypass -File .\build.ps1

脚本依次做：检查环境 → 清理（`-Clean`）→ 生成图标（`media\tiles\6m.svg` → `build\icon.ico`，图案按 `--content-scale 0.84` 收缩、四周留白）→ 跑回归（`test\apptest.js` + `test\naga_test.py` + `test\mortal_test.py`）→ 用 PyInstaller 把后端打成 `dist\pyi\tenhou-paipu-analysis-server\`（onedir，内嵌 `node.exe`）→ 冒烟测试（`-Smoke`）→ electron-builder 打 NSIS 安装包到 `dist\electron\`。

常用开关：`-SkipIcon`、`-SkipTests`、`-FullTests`（加跑需要真实数据目录的 `test\datamgr_test.py`）、`-SkipPyi`、`-SkipElectron`、`-Clean`、`-Smoke -Port 8788`、`-PythonExe <路径>`、`-NodeExe <路径>`。也可以 `npm run build` / `npm run dist`。

**产物**：`dist\electron\tenhou-paipu-analysis-<package.json 的 version>-setup.exe`（NSIS，安装路径可选；v1.3.0 即 `tenhou-paipu-analysis-1.3.0-setup.exe`）。安装后：

- 程序装在自选目录（**默认 `C:\Program Files\tenhou-paipu-analysis`**，按「所有用户」安装：安装时会弹 UAC 要管理员权限；最后一步的目录页里仍可改成别的路径）；
- 后端与 Node 在 `<安装目录>\resources\backend\`；
- 牌谱与数据库固定放**当前 Windows 用户**的 `%LOCALAPPDATA%\tenhou-paipu-analysis\data\{paipu,db}`（多用户各一份，界面「本地数据管理」页签里管理）；
- 「牌谱播放 → 浏览选择…」由 Electron 主进程弹原生文件框，默认定位到上面的 `data\paipu`（`desktop/preload.js` 暴露 `window.tenhouDesktop`，主进程 `ipcMain.handle('pick-paipu-file')`；路径来自后端 `/api/health` 的 `paipu_dir`，目录不存在时会先建出来）；浏览器模式没有这个桥，退回浏览器自带文件框。
- 卸载时会询问是否一并删除上面这个数据目录，**默认不删除**（询问框的默认按钮就是「否」，直接回车即保留；静默卸载 `/S` 也一律保留）；卸载程序是提权运行的，问的是**执行卸载的那个卸载者**的数据目录。

**参考指纹**（第 25 轮实测，用户本机构建）：`tenhou-paipu-analysis-0.1.0-setup.exe` = 142,676,228 B，SHA256 `CCFAD901B86E142B17248C34C5E645971AE05F715C84940E27BB123B86E2F2B9`（重新打包会因时间戳 / 压缩差异得到不同哈希，此值只用于核对同一次分发的产物）。同一轮的全量回归（9 个测试全绿）见 `log.md` 第 21.11 节。 **第 67 轮实测（v1.3.0，用户本机）**：`tenhou-paipu-analysis-1.3.0-setup.exe` = 143,283,273 B，SHA256 `2BEFAB2C1025ED1C212966ACF899E4ACBBA9605DA847A3A45A5A30F824AAC376`（后端 `_ssl` 修复 + 图标图案 0.84 收缩后的产物）。

**注意**

- PyInstaller 的参数只有一份，写在 `packaging\pyi_build.py`（它会打印等价命令）；受限终端里若 hook 发现报 `PermissionError [WinError 5] / create_pipe`，`build.ps1` 会自动加 `--in-process` 兜底。
- **OpenSSL（第 67 轮修的真 bug）**：PyInstaller 会从 conda 的 **base** 环境（如 `D:\coding\anaconda3\Library\bin`）抓 `libssl-3-x64.dll` / `libcrypto-3-x64.dll`，它们与本环境 `DLLs\_ssl.pyd` 不配套 ⇒ 打包后端一启动就 `ImportError: DLL load failed while importing _ssl: 找不到指定的程序`（`-Smoke` 会立刻发现）。`packaging\pyi_build.py` 现在会用 `<本环境>\Library\bin\` 的那一对 `--add-binary` 进包，并在打包后按 SHA256 校验、不一致就覆盖（打印 `OpenSSL : … 已替换 …`）。
- electron-builder 需要能用匿名管道启动子进程（`npm`、`makensis`）；日志里若出现 `spawn EPERM` / `EPERM: operation not permitted`，换普通终端重跑。
- 关掉依赖重建写在 `package.json` 的 `build.npmRebuild = false`；不要在命令行写 `-c.npmRebuild=false` —— 某些 shell 下 electron-builder 会把它当成**配置文件路径**，直接报 `ENOENT: no such file or directory, open '...\.npmRebuild=false'`。
- 默认装到 Program Files 由 `package.json` 的 `build.nsis.perMachine = true` 决定；改成 `false` 会退回 `%LOCALAPPDATA%\Programs\<应用名>`（并且 assisted installer 会多一个「安装模式」页，默认选「仅为我安装」）。
- 目前没有代码签名，安装时 SmartScreen 会提示「未知发布者」。
- 只支持 Windows x64。图标可由 `tools\svg2ico.py` 从素材复现，不需要外部图片；`--content-scale` 控制牌面图案相对牌面矩形的缩放（1 = 铺满，`build.ps1` 用 **0.84**），牌面白底不缩、只把图案围绕牌面中心收缩，于是四周留出更宽的白边（用户 m08700，与界面里牌图的白边一致）。
- 首次打包时 `electron-builder` 会从 GitHub 下载 `winCodeSign-2.6.0.7z`（约 4.6 MB）；若网络被重置（`read ECONNRESET`），可把该文件手动放到 `%LOCALAPPDATA%\electron-builder\Cache\winCodeSign-2.6.0\winCodeSign-2.6.0.7z`（sha256 `cdaec7154dda7cc31f88d886e2489379a0625a737d610b5ae7f62a12f16743aa4`）—— `electron-builder` 会先校验缓存里的文件、命中就不再联网（用户 m08849 实测）；也可设 `ELECTRON_BUILDER_BINARIES_MIRROR`（或 `NPM_CONFIG_ELECTRON_BUILDER_BINARIES_MIRROR`）走镜像。
- 卸载询问写在 `packaging\installer.nsh` 的 `customUnInstall` 里。注意按「所有用户」安装时（`perMachine: true`）卸载器的 shell 变量上下文是 `all`，`$LOCALAPPDATA` 会被解析成 `C:\ProgramData` ⇒ 宏里先 `SetShellVarContext current` 再定位数据目录、之后切回 `all`，否则询问永远不会出现（细节与实测见 `log.md` 踩坑 96）。
